# Portfel Music — техническое задание и план самостоятельной разработки

**Версия:** 1.0 · **Формат:** учебный веб-проект для портфолио · **Срок:** 6 недель при ~10–15 часах в неделю

## 1. Что строим

Portfel Music — веб-приложение с каталогом музыки, воспроизведением и визуализацией звуковой волны. Гость слушает опубликованные треки и ищет музыку. Зарегистрированный пользователь дополнительно ставит лайки, собирает плейлисты и видит историю прослушивания. Сотрудник (staff) добавляет разрешённые для публикации записи через Django Admin.

**Цель проекта:** самому пройти полный цикл: спроектировать данные и API, загрузить и обработать аудио, реализовать HTTP Range, собрать устойчивый React-плеер, запустить сервисы в Docker и настроить CI. Этот документ задаёт поведение и критерии проверки, но не подменяет собственную реализацию готовым кодом.

### Границы MVP

| Входит в обязательный результат | Остаётся расширением |
| --- | --- |
| Каталог артистов, альбомов/синглов и треков; поиск по названию и артисту; фильтр по жанру | Подписки на артистов или друзей, социальные уведомления |
| Регистрация, вход по JWT; профиль; лайки; личные и публичные плейлисты; история | Рекомендации, радио, еженедельные чарты |
| Загрузка staff через Django Admin; асинхронная обработка; waveform | Пользовательские загрузки, модерация, несколько битрейтов |
| Плеер, очередь в текущей вкладке, пауза, перемотка, следующий/предыдущий, громкость | Синхронизация очереди между устройствами, офлайн-режим |
| Публичная выдача **только опубликованного разрешённого аудио** с поддержкой одного HTTP Range | Платная подписка, DRM, многодиапазонные Range-запросы |

Нет страницы загрузки для обычного пользователя: каталог наполняется staff, поэтому в первой версии не требуется система проверки чужого контента. Для демо используй собственные записи, треки с подходящей лицензией или записи с явным разрешением правообладателя; источник и лицензию сохрани в записи трека.

## 2. Стек и согласованные решения

| Слой | Выбор | Для чего |
| --- | --- | --- |
| API и админка | Django 5.x, Django REST Framework | Модели, права доступа, каталог, личные действия |
| Вход | Simple JWT | JWT для React-клиента; штатная Django session для `/admin/` |
| HTTP-сервер | Daphne / ASGI | Размещение Django; потоковый ответ должен использовать **асинхронный** итератор |
| Интерфейс | React 18, React Router, Zustand, wavesurfer.js **7.x** | SPA и единый живущий между страницами плеер |
| Объекты | MinIO, приватный bucket; boto3 / django-storages | Исходные MP3 и обложки; MinIO не отдаётся браузеру напрямую |
| Фоновые задачи | Celery, Redis; `ffprobe`, `ffmpeg`, librosa | Проверка аудио и вычисление готовых пиков |
| База | PostgreSQL | Каталог и пользовательские данные |
| Входной сервер | Nginx | React build, `/api/`, `/admin/`, отключение буферизации для аудио |
| CI | GitHub Actions | Проверки API, сборка интерфейса, линтеры |

**Почему исходные 7 сервисов стали 6 в MVP:** `celery-beat` не выполняет полезной работы, пока нет периодического чарта; он добавляется с функцией чарта. `Django Channels` тоже подключается тогда, когда появится конкретный WebSocket-сценарий, например уведомление о готовности загрузки. Daphne уже обслуживает HTTP без Channels. Redis в MVP работает брокером Celery; после добавления Channels он также будет channel layer через `channels_redis`. Не включай процессы просто ради упоминания технологий в резюме.

**Одно происхождение для браузера:** Nginx отдаёт SPA и проксирует `/api/` на Django. В `src` плеера ставится URL вида `/api/v1/tracks/{id}/stream/`. React не получает внутреннее имя `minio`, ключи S3 или presigned URL. API опубликованных треков и их поток публичны; JWT нужен для профиля, истории, лайков и плейлистов. Это позволяет нативному аудиоэлементу делать Range-запросы без нестандартной передачи Bearer-заголовка.

## 3. Пользовательские сценарии и экраны

1. **Главная/каталог:** список опубликованных треков, переход к альбому/артисту, запуск воспроизведения. Есть загрузка, пустое состояние и сообщение об ошибке.
2. **Поиск:** запрос `q` по названию трека и имени артиста без учёта регистра; отдельный фильтр `genre`; постраничная выдача. Пустая строка возвращает каталог, не ошибку.
3. **Артист и альбом:** bio/обложка артиста, альбомы и синглы, только опубликованные треки. В альбоме порядок по номеру трека.
4. **Плеер:** один экземпляр в корне приложения; старт по нажатию, play/pause, seek по waveform, прогресс и длительность, громкость, следующий/предыдущий. Очередь существует в одной вкладке, при смене страницы звук продолжается; при обновлении страницы автоматического запуска нет.
5. **Учётная запись:** регистрация, вход, выход, просмотр/редактирование своего профиля. Гость видит предложение войти, когда пытается лайкнуть или создать плейлист.
6. **Плейлисты:** создать, переименовать, удалить, изменить публичность; добавить/удалить трек и поменять порядок. Владелец управляет своим плейлистом; другой пользователь видит только публичный. Повторное добавление того же трека не допускается.
7. **История и лайки:** история по последней активности, продолжение с сохранённой позиции; список любимых треков. При снятии лайка запись удаляется.
8. **Админка:** staff создаёт артиста и альбом/сингл, загружает MP3 с названием, номером в альбоме и данными о праве на публикацию; видит статусы обработки и текст ошибки. Обычный пользователь в админку не входит.

## 4. Данные и правила целостности

Создай собственную модель `User(AbstractUser)` **до первой миграции**. Идентификаторы могут быть обычными `BigAutoField`: усложнять проект UUID для всех таблиц не требуется.

| Модель | Основные поля и связи | Инварианты |
| --- | --- | --- |
| `User` | `username`, `email`, `avatar_file` (необязательно), даты | `username` уникален; email при регистрации нормализован и уникален; `is_staff` управляет загрузкой |
| `Artist` | `name`, `bio`, `cover_file` | Артист не связан автоматически с аккаунтом `User`; название непустое |
| `Album` | `artist` FK, `title`, `kind: album/single`, `genre`, `release_year`, `cover_file` | Любой трек принадлежит одному альбому или синглу; год реалистичен; жанр берётся из фиксированного списка MVP |
| `Track` | `album` FK, `title`, `track_number`, `audio_file` (ключ в MinIO), `byte_size`, `duration_seconds`, `waveform_data` JSON, `status`, `is_published`, `error_message`, `upload_revision`, `source_credit`, `license_note` | `status: pending → processing → ready/failed`; `duration_seconds > 0` и непустые пики обязательны для `ready`; уникальны `(album, track_number)` |
| `Playlist` | `owner` FK `User`, `title`, `is_public`, `created_at`, `updated_at` | Право изменения только у владельца; название непустое |
| `PlaylistTrack` | `playlist` FK, `track` FK, `position`, `added_at` | Уникальны `(playlist, track)` и `(playlist, position)`; перестановка атомарна; выдача по `position` |
| `Like` | `user` FK, `track` FK, `created_at` | Уникальна пара `(user, track)` |
| `ListenHistory` | `user` FK, `track` FK, `client_session_id`, `started_at`, `last_played_at`, `progress_seconds`, `completed_at` nullable | Одна запись на запуск прослушивания; уникальна `(user, client_session_id)`; позиция в диапазоне от 0 до длительности |

`PlaylistTrack` — обязательная промежуточная таблица: голое M2M не хранит управляемый порядок. `ListenHistory` — события отдельных прослушиваний, а не новая строка на каждый `timeupdate`. Внешние ключи каталога защищаются от случайного удаления (`PROTECT`); трек, который уже есть в пользовательских данных, скрывается через статус/снятие с публикации, а не удаляется физически. `is_published` по умолчанию `false`; установить `true` можно только при `status=ready` и заполненных `source_credit`/`license_note`. API показывает только `status=ready AND is_published=true`. В ТЗ далее слово «опубликованный» означает именно это условие.

**Права на старые связи:** при снятии трека с публикации история и позиции плейлистов остаются в базе, но клиент показывает «недоступен» и не включает его в очередь; прямой streaming URL начинает возвращать `404`. Прямое повторное добавление недоступного трека запрещено.

**Индексы:** на `Track(status, is_published)`, `Album(artist, genre)`, `ListenHistory(user, last_played_at)`; уникальные ограничения выше создают нужные индексы для лайков и позиций. Для небольшого учебного каталога поиск через `icontains` достаточен; полнотекстовый поиск пока не нужен.

## 5. Контракт API (`/api/v1/`)

Ответы JSON, даты ISO 8601 в UTC, ошибки в одном согласованном формате (`code`, `detail`, при валидации — `fields`). Списки с пагинацией: `count`, `next`, `previous`, `results`, по умолчанию 20 элементов. В detail трека есть относительный `stream_url`; **нет** прямого MinIO URL. Каталог показывает только опубликованное. Пользовательские запросы передают `Authorization: Bearer <access>`.

| Метод и путь | Доступ | Результат / правило |
| --- | --- | --- |
| `POST /auth/register/` | Все | Создать аккаунт; 201; пароль проходит Django validators |
| `POST /auth/token/`, `POST /auth/token/refresh/` | Все/с refresh | Получить/обновить пару токенов (Simple JWT) |
| `POST /auth/logout/` | Вошедший | Поместить refresh в blacklist и очистить токены на клиенте |
| `GET/PATCH /me/` | Вошедший | Просмотр/изменение своего профиля |
| `GET /tracks/?q=&genre=&page=` | Все | Каталог; поиск по track title и artist name, фильтр по album genre |
| `GET /tracks/{id}/` | Все | Название, артист, альбом, длительность, пики, stream URL, статус лайка для вошедшего |
| `GET/HEAD /tracks/{id}/stream/` | Все | `200`, `206`, `416` по правилам раздела 6; только опубликованный трек |
| `GET /artists/`, `GET /artists/{id}/` | Все | Список и detail артиста с видимыми релизами |
| `GET /albums/{id}/` | Все | Релиз и треки по `track_number` |
| `GET /artists/{id}/cover/`, `GET /albums/{id}/cover/`, `GET /users/{id}/avatar/` | Все | Небольшие изображения через Django; `404`, если нет изображения |
| `GET /playlists/`, `POST /playlists/` | Вошедший | Список своих / создание |
| `GET /playlists/{id}/` | Все с учётом приватности | Владелец или публичный плейлист; чужой приватный — `404` |
| `PATCH/DELETE /playlists/{id}/` | Владелец | Изменить заголовок/публичность, удалить |
| `POST /playlists/{id}/tracks/` | Владелец | Добавить опубликованный трек, в конец; дубль — `409` |
| `DELETE /playlists/{id}/tracks/{track_id}/` | Владелец | Удалить, нормализовать позиции |
| `PUT /playlists/{id}/order/` | Владелец | Массив всех текущих track IDs в новом порядке; одной транзакцией |
| `GET /me/likes/`, `PUT/DELETE /tracks/{id}/like/` | Вошедший | Список, идемпотентная установка/снятие лайка |
| `GET /me/history/` | Вошедший | Последние сессии прослушивания |
| `POST /me/history/`, `PATCH /me/history/{id}/` | Вошедший | Создать с `client_session_id`, обновить прогресс/завершить только свою запись |

`PUT /tracks/{id}/like/` возвращает `200/201`, даже если лайк уже существует; `DELETE` — `204`, даже если записи уже нет. `POST /auth/logout/` принимает refresh-токен в теле запроса. Добавление в плейлист и смена порядка должны быть защищены уникальными ограничениями и транзакцией, а не только проверками на фронтенде; при перестановке позиций избежать временного конфликта уникальности (например, через отложенное ограничение PostgreSQL или двухэтапную замену). Для API не предусмотрена публичная запись артистов, альбомов или треков: загрузка через `/admin/`.

**JWT для этого MVP:** access примерно 15 минут, refresh примерно 12 часов; оба хранятся в `sessionStorage` этой вкладки. На перезагрузке фронтенд может восстановить вход, при закрытии вкладки пользователь входит снова. При `401` выполнить одну попытку refresh, затем повторить запрос; если не удалось — выйти. Refresh blacklist включён. Это сознательное упрощение учебного SPA; токены в JavaScript подвержены риску XSS, поэтому не рендери непроверенный HTML и не добавляй сторонние скрипты без необходимости. Админка использует обычную Django session/CSRF отдельно от SPA.

## 6. Потоковое аудио и HTTP Range

**Маршрут данных:** браузер → Nginx → Django endpoint → приватный MinIO по внутренней Docker-сети → Django → браузер. API сначала проверяет, что запись опубликована, затем запрашивает **только нужный диапазон** объекта у MinIO. Django отдаёт ответ постепенно, не читая весь MP3 в память.

У `Track` хранится размер оригинального объекта в байтах и ключ; при замене файла обновляются ключ/размер и `upload_revision`. Объект считается неизменяемым для опубликованной версии. Чтобы ASGI не собрал синхронный итератор целиком в память, используй асинхронное чтение ответа MinIO и асинхронный итератор `StreamingHttpResponse`; закрывай upstream-соединение при завершении или отключении клиента. Возможный учебный путь: подписанный URL, созданный **только для внутреннего адреса MinIO**, плюс асинхронный HTTP-клиент для чтения upstream. Это внутренний механизм; в JSON и браузер этот URL не попадает. Для метаданных и загрузки файлов можно отдельно использовать boto3/django-storages.

| Запрос | Ответ | Обязательные заголовки/поведение |
| --- | --- | --- |
| `GET` без `Range` | `200 OK` | `Content-Length: S`, `Content-Type: audio/mpeg`, `Accept-Ranges: bytes`; поток всех `S` байт |
| `GET Range: bytes=a-b` | `206 Partial Content` | `Content-Range: bytes a-b/S`, `Content-Length: b-a+1`; читать ровно этот участок |
| `GET Range: bytes=a-` | `206` | От `a` до `S-1` |
| `GET Range: bytes=-n` | `206` | Последние `min(n, S)` байт |
| `GET Range` с началом `a >= S` | `416 Range Not Satisfiable` | `Content-Range: bytes */S` |
| `HEAD` (с Range или без) | Аналогичные код и заголовки | Тела ответа нет; не скачивать MP3 |

`S` — фактический размер объекта. Если `b >= S`, ограничить конец значением `S-1`; для суффикса `n` должно быть положительным числом. Если `a > b` после нормализации, вернуть `416`. В MVP поддерживается ровно **один** байтовый диапазон: неверный синтаксис или `bytes=0-1,3-4` дают `400`, а не «частичный ответ» без соответствующего тела. Не путай `206` (выбор диапазона байт) с `Transfer-Encoding: chunked` (способ передачи HTTP-ответа). `Range: bytes=0-` тоже должен давать `206`. Не обещай поддержку `If-Range` или многодиапазонных запросов в этой версии.

Nginx не буферизует этот маршрут (`proxy_buffering off` для streaming path); upstream и браузер не должны получать закрытый MinIO endpoint. Для отсутствующего/скрытого трека — `404`, временная недоступность хранилища — `503` и запись ошибки в лог. Не раскрывать ключи объектов и секреты в тексте ошибок. Поток публичен **только для разрешённых к публикации записей**: прямой URL не обходит состояние `is_published`.

**Проверка вручную:** выдать запросы без Range, `bytes=0-1023`, `bytes=1024-`, `bytes=-256`, `bytes=S-`, некорректный Range и `HEAD`; сверить код, длину тела, `Content-Range` и реальное воспроизведение/seek в браузере. Отдельно убедиться, что на файле около 20 МБ процесс Django не удерживает весь файл в RAM на одного слушателя.

## 7. Загрузка и подготовка waveform

1. Staff заполняет `Artist` и `Album`, загружает MP3 через Admin. Сервер проверяет файл **по содержимому** через `ffprobe`, а не только по расширению; лимит MVP — 30 МиБ и 15 минут, аудиоформат MP3. В админке нельзя выбрать уже занятый `track_number` для релиза.
2. Файл попадает в приватный MinIO bucket под уникальным ключом, например с ID трека и новой ревизией. В БД фиксируются ключ, `byte_size`, `status=pending`, `upload_revision`. После успешного коммита транзакции ставится задача Celery с `(track_id, upload_revision)` через `transaction.on_commit()` / `delay_on_commit()`.
3. Worker переводит **эту ревизию** в `processing`, скачивает объект во временный файл, проверяет длительность и декодирует через `ffmpeg` в моно PCM; librosa используется для извлечения и нормализации пиков. Ограничения размера и времени процесса защищают от зависания на повреждённом файле.
4. Сформировать 800 временных окон; в каждом сохранить min и max амплитуды, всего 1600 значений в одном канале, нормализованных в `[-1, 1]`. Сохранить `waveform_data` как `[[...1600 чисел...]]` (массив каналов) и `duration_seconds` из оригинального файла, округлив для API до десятых/сотых секунды. Для `ready` нужны корректная длительность и непустой массив.
5. При успехе `status=ready`, затем staff включает `is_published`; при ошибке — `failed` и короткое диагностическое сообщение для staff. Сбой MinIO/сети допускает ограниченные повторные попытки, повреждённый файл не повторяется бесконечно. Повторная задача и результат старой ревизии не должны перезаписывать новую загрузку. Временный файл всегда удаляется.

`wavesurfer.js 7.x` получает URL потока, **заранее посчитанные пики** и `duration_seconds`. Так библиотека рисует волну без полного декодирования файла в браузере; звук играет через media element. Если длительность равна нулю или формат JSON неправильный, трек не публикуется. На карточках каталога можно не отправлять waveform: полный массив нужен на detail/при выборе трека, чтобы не раздувать список.

Изображения ограничить, например, 2 МиБ и разрешёнными MIME (JPEG/PNG/WebP). Приватный bucket не означает, что `<img>` автоматически увидит файл: предусмотренные в API публичные image endpoints возвращают маленькие изображения через Django без ссылки на внутренний MinIO. Аватар в этом проекте считается публичной частью профиля; не загружай чувствительные фото.

## 8. Плеер и фиксация истории

- Единственный `PlayerShell` монтируется над маршрутизируемыми страницами. Создай один экземпляр wavesurfer/media element и освобождай его только при размонтировании всего приложения; отдельные карточки треков управляют им через Zustand. Повторное нажатие на текущий трек переключает play/pause, выбор нового меняет источник.
- Zustand хранит `currentTrackId`, очередь `trackIds`, индекс, `isPlaying`, `currentTime`, `volume` и действия управления. Источник истины для времени и факта воспроизведения — события media element; не поддерживай второе независимое аудио на странице.
- Очередь формируется из текущего контекста (альбом, плейлист или выдача поиска) только из доступных треков. После `ended` — следующий, после последнего — остановка. При удалении/снятии с публикации трека — понятная ошибка и пропуск недоступного элемента.
- Для истории авторизованного пользователя: после **30 секунд реального воспроизведения** создать сессию с клиентским UUID; обновлять позицию раз в 15–30 секунд и при pause/смене трека, если есть сеть. Seek сам по себе не считается прослушиванием. Повтор POST с тем же `(user, client_session_id)` возвращает существующую запись. По завершении поставить `completed_at`; прогресс не может превысить длительность.
- Для «Продолжить»: взять последнее событие пользователя по треку; если завершено, начать с 0, иначе предложить позицию. Гостям история на сервере не пишется. Браузер может блокировать autoplay: воспроизведение запускается явным действием пользователя.

## 9. Запуск, конфигурация и структура проекта

```text
portfel-music/
├── backend/
│   ├── config/             # settings, urls, asgi, celery
│   ├── accounts/           # User, auth, profile
│   ├── catalog/            # Artist, Album, Track, поиск, images, streaming
│   ├── library/            # Playlist, PlaylistTrack, Like, ListenHistory
│   └── tests/              # важные сценарии и Range
├── frontend/
│   └── src/                # routes, api, features, player, store
├── nginx/                  # SPA + proxy
├── .github/workflows/
├── compose.yml
├── .env.example
└── README.md
```

| Контейнер MVP | Назначение |
| --- | --- |
| `postgres` | База, persistent volume |
| `redis` | Broker Celery |
| `minio` | Приватный bucket, persistent volume; порт API не открывать наружу в deployment |
| `django` | Daphne/ASGI, REST, Admin и streaming |
| `celery` | Обработка загруженных треков; установлены `ffmpeg`/`ffprobe` и аудиозависимости |
| `nginx` | Внешний HTTP вход; статический build React и проксирование API |

В dev React/Vite работает локально отдельной командой и проксирует `/api/` к Nginx; в итоговой сборке React собирается на build-этапе образа Nginx, поэтому постоянный `frontend` контейнер не нужен. Миграции и создание bucket выполняются отдельной документированной командой подготовки, а не гонкой при одновременном старте нескольких контейнеров. Healthchecks проверяют PostgreSQL, Redis и MinIO; зависимости контейнеров не заменяют проверки готовности.

`.env.example` перечисляет `DJANGO_SECRET_KEY`, `DEBUG`, `ALLOWED_HOSTS`, доступ к PostgreSQL/Redis/MinIO, имя bucket и публичный origin; настоящие секреты и `.env` не коммитятся. В prod — HTTPS, `DEBUG=False`, настроенные trusted origins, разумные лимиты загрузки и доступ к Admin только по HTTPS. Бэкап нужен для PostgreSQL **и** MinIO volume: без любого из них каталог окажется неполным.

## 10. Критерии качества и проверки

| Область | Минимальная проверка |
| --- | --- |
| Модели/права | Нельзя создать второй лайк, второй одинаковый трек в плейлисте, одинаковую позицию; чужой приватный плейлист не читается и не редактируется |
| Загрузка | Реальный MP3 проходит в `ready`; повреждённый/слишком большой отклоняется или получает `failed`; результат старой задачи не затирает новую ревизию |
| Streaming | Тесты на `200`, `206` для трёх форм Range, `416`, `HEAD`, неправильный/multi Range, скрытый трек, отказ MinIO; байты ответа сравниваются с исходным файлом |
| Плеер | В Chrome/Firefox: seek в середину, смена страницы без остановки, смена трека без второго звука, завершение очереди, восстановление после сетевой ошибки |
| История | Ни одна запись не создаётся раньше 30 секунд звучания; повторы POST идемпотентны; прогресс можно получить на другом экране |
| Сборка | Чистый запуск по README, миграции, тестовый staff, демонстрационные лицензированные треки; API-тесты, frontend lint/build в CI |

Нагрузочная цель для локального портфолио, не обещание production scale: несколько одновременных слушателей 20–30 МиБ файлов без пропорционального размеру файла роста памяти Django. Зафиксируй способ замера и результат в README. В логах достаточно ID трека, статуса ответа, ошибок worker и времени обработки; не логируй токены, пароли и целые presigned URLs.

## 12. Дополнительные функции: порядок и новые сущности

1. **Транскодинг:** после проверки оригинала сделать отдельные версии MP3 `128k/320k` через ffmpeg. Добавить `TrackAudioVariant(track, bitrate, object_key, byte_size, status)` и параметр качества. Каждый вариант получает собственные Range и длительность, которую сверяешь с исходной. Не переиспользовать `byte_size` оригинала для другого файла.
2. **Еженедельный чарт:** добавить `celery-beat` **седьмым контейнером**, `WeeklyChart(week_start, track, listens_count, rank)`. Раз в неделю агрегировать сессии из `ListenHistory` по UTC-неделе: каждая сохранённая сессия означает минимум 30 секунд звучания, один `client_session_id` учитывается один раз. Недельный пересчёт идемпотентен. Только здесь появляется задача scheduler.
3. **Радио:** построить простой порядок рекомендаций по жанрам прослушанных/лайкнутых треков; исключить скрытые и уже стоящие в очереди. Сначала записать базовую формулу и проверить её на нескольких историях без ML.
4. **Channels и уведомления:** реальный сценарий — staff получает событие `track.ready` после Celery-обработки, либо пользователь получает уведомление о лайке друга. Для второго сценария сначала ввести `Follow(follower, followed)` и `Notification(recipient, actor, kind, track, created_at, read_at)`; слово «друг» иначе не определено. Добавить `channels_redis`, routing и WebSocket consumer, проверять origin и права. JWT из SPA сам по себе **не аутентифицирует WebSocket**: определить отдельный короткоживущий одноразовый WS-ticket, выдаваемый защищённым API, и обменять его на user ID при подключении. Не передавать основной JWT в URL и не отправлять событие всем клиентам.

Бонусные функции не считаются частью критерия готовности MVP. Для резюме упоминай Channels, Beat или транскодинг как реализованные технологии только после рабочего сценария и проверки.

## 13. Контрольный список завершения

- [ ] Обычный пользователь проходит регистрацию → поиск → play/seek → лайк → создание плейлиста → историю.
- [ ] Staff добавляет MP3, видит `pending/processing/ready/failed`, публикует только `ready` с указанными правами на запись.
- [ ] Range работает по фактическим байтам; большой файл не загружается целиком в браузер ради waveform и не буферизуется целиком Django.
- [ ] Один поток звука переживает переходы между React-страницами; при refresh не начинается autoplay.
- [ ] Приватные данные защищены на сервере; скрытый трек нельзя открыть прямым streaming URL.
- [ ] `docker compose` и README воспроизводят запуск с нуля; CI запускает осмысленные проверки; в репозитории нет секретов или чужой музыки без лицензии.
- [ ] В README есть архитектура, ключевые решения, ограничения MVP, скриншоты, тестовые команды и честный список следующих шагов.
